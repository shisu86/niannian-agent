# 念念 · S10 评估报告

> 评估日期：2026-11-27
> 环境：Windows 11 / Python 3.12 / 单进程 uvicorn / SQLite（WAL）
> 模型：DeepSeek-chat（OpenAI SDK 兼容接口）
> 复现：`scripts/eval_recall.py`、`scripts/eval_latency.py`

## 1. 评估什么

这个项目有三个容易"感觉良好但说不清"的地方，评估只回答这三个问题：

| 问题 | 指标 | 为什么重要 |
|---|---|---|
| 该想起的事，想得起来吗？ | Recall@5 / MRR / 噪音率 | 记忆是产品核心，检索不准等于没记 |
| 模型抽风时，系统还稳吗？ | 降级率 / 危机召回 | 陪伴产品不能因为一次超时就崩 |
| 用户要等多久？ | 首 token / 检索耗时 | 超过 2 秒，陪伴感直接变机器感 |

## 2. 检索质量（Recall@5）

**数据集**：30 条标注记忆，六类全覆盖（事实 8 / 偏好 7 / 事件 5 / 关系 2 / 待跟进 2 / 摘要池 6），
分属 3 个角色；20 个查询，分三组。

| 指标 | 结果 |
|---|---|
| **Recall@5** | **93.3%**（14/15） |
| **MRR** | **0.933** |
| 平均噪音率 | 8.3% |
| 角色隔离 | 3/3 通过 |
| 共享事实可见 | 2/2 通过 |

**解读：**

- 14 个可命中查询里，13 个的正确答案排在第 1 位，1 个未命中。
- 噪音主要集中在"住在哪里"这类查询——OR 降级把含"用户"的共享事实一起捞了回来，
  但正确答案仍排第 1，重排公式把它们压到了后面。
- **隔离全部正确**：角色 A 检索不到角色 B 的私人记忆（冰美式 / 打球 / 大学室友），
  说明 `(persona_id = ? OR scope = 'shared')` 这个条件按设计工作。
- **共享全部正确**：角色 B 能检索到角色 A 写入的基础事实（住址、过敏）。

**失败案例（如实记录）：**

| 查询 | 应命中 | 实际 | 原因 |
|---|---|---|---|
| 多少岁 | 用户今年二十六岁 | 0 条 | 词面不匹配：查询切出"多少/岁"，记忆切出"二十六/岁"，AND 失败，OR 后"多少"无对应 token |

这不是 bug，是**纯关键词检索的固有局限**：能覆盖词面重合的表达，覆盖不了同义改写。
后续接入 Embedding 做混合检索是明确的改进方向（`search(mode="hybrid")` 已预留接口并显式拒绝，不做静默降级）。

## 3. 稳定性（降级率与危机召回）

**方法**：20 句典型输入直接过 `analyze` 节点，统计模式分布。

| 输入类型 | 数量 | 结果 |
|---|---|---|
| 正常闲聊 | 5 | 全部走模型，risk=normal |
| 情绪低落 | 3 | 2 句 elevated，1 句 normal |
| 危机表达 | 5 | **5/5 判定为 crisis** |
| 短问候 | 3 | 全部 normal（未被历史带偏） |
| 长句 | 2 | 全部 normal |
| 无意义短句 | 2 | 全部 normal |

| 指标 | 结果 |
|---|---|
| **模型解析降级率（rule_fallback）** | **0%**（0/20） |
| **危机召回** | **5/5 = 100%** |
| analyze p50 | 约 800 ms |

**一个值得说的细节：**

5 句危机表达里，**只有 1 句被规则词表直接命中**（"我不想活了"），
其余 4 句（割腕、一了百了、活着没意思、想结束一切）都是模型判定后经**二次确认**保持 crisis。

这说明安全链路是三层的：

1. 规则词表——零延迟、零成本，但覆盖不全；
2. 模型判断——覆盖语义，但会误报；
3. 二次模型确认——专门压制"历史污染导致的误报"，确认失败时保持高风险。

**不把安全押在任何单一机制上**，这也是为什么不能只做关键词黑名单。

## 4. 延迟

### 4.1 检索耗时（本地，500 条记忆 × 100 次）

| 指标 | 结果 |
|---|---|
| p50 | **2.2 ms** |
| p95 | 2.6 ms |
| max | 3.9 ms |

检索不是瓶颈，可以忽略。

### 4.2 对话延迟（真实服务 × 6 轮）

| 指标 | 结果 |
|---|---|
| **首 token p50** | **1085 ms** |
| 首 token max | 1120 ms |
| 总时长 p50 | 1390 ms |
| 总时长 max | 1613 ms |

**瓶颈分析：**

首 token ≈ analyze（约 800 ms）+ generate 首 token（约 300 ms）。
**analyze 占了首 token 延迟的七成**——因为它要先产出意图、情绪、风险和多条检索 query，
才能决定走哪个分支、检索什么。

这解释了架构上的取舍：检索只有 2 ms，却必须排在 analyze 之后，
因为 query 由 analyze 生成。想进一步压缩首 token，方向是：
- 缩短 analyze 的 prompt 与输出 schema；
- 对明显不需要检索的短句跳过 analyze（当前只对危机词做了规则直通）；
- 用更快的模型做 analyze、主模型负责生成。

## 5. 局限

诚实记录，避免"自己出题自己考"的误读：

1. **测试集是自造的**，30 条记忆、20 个查询均按项目设计手工编写，
   存在选择偏差；查询偏关键词化，不完全代表真实用户的多轮自然表达。
2. **样本量小**，单次运行，没有做多次重复的置信区间。
3. **未做消融对比**：没有测"去掉重要性/新近度重排"后的 Recall 变化，
   因此无法量化重排公式每一项的贡献。
4. **延迟受网络与模型服务波动影响**，数值只代表本次测试时段。
5. **角色隔离只测了检索层**，没有测 LLM 在回答中是否可能通过共享事实反推出其他角色的信息。

## 6. 结论

| 维度 | 结论 |
|---|---|
| 检索质量 | 词面可覆盖的场景下可靠（Recall@5 93.3%），同义改写是已知短板 |
| 多角色隔离 | 检索层完全正确，共享/私有的边界符合设计 |
| 稳定性 | 单次评估零降级，危机召回 100%；三层安全链路有效 |
| 延迟 | 首 token 约 1.1 秒，瓶颈在 analyze，不在检索 |
| 下一步 | 混合检索（Embedding + FTS）、analyze 提速、消融实验 |
